# Playbook: slg (Plan and set org-level Local Agent caps for every org)

Recommend an explicit **org-level Local Agent cap** for **every billing organization**, distributing `DAG_MONTHLY_ACU_POOL` proportionally to each org's current-cycle Local Agent consumption, then — after the write gate — PATCH all of them and live-verify. This is the **playbook twin of `dag set limit global <acus>`**: that command writes one explicit user-supplied number deterministically; `dag slg` computes the per-org numbers from live consumption and writes the whole layer in one confirmed batch. It is also not `dag set-limits-global`, which only seeds caps for currently-uncapped orgs zero-sum from capped-org headroom — `slg` replans every org, capped or not.

All numbers come from `org_caps_jq` (hard rule 1). Σ proposed caps never exceeds the pool; every org keeps at least `ceil(local_consumed) + min_headroom`, so no org is ever insta-blocked by the new cap.

## Steps

1. **Cycle dates.** GET `/v3/enterprise/consumption/cycles`. Current cycle = item with `after <= now < before`. Compute `days_left` from epoch arithmetic and show the calculation (hard rule 9).
2. **Org roster.** GET `/v3/enterprise/organizations` — `items[]` of `{org_id, name, max_session_acu_limit, max_cycle_acu_limit}`. Every billing org is in scope.
3. **Per-org Local Agent consumption.** For each org, GET `/v3/enterprise/consumption/daily/organizations/{org_id}` with the cycle's `time_after`/`time_before`. The org gate governs Local Agent only, so `local_consumed` = Σ over `consumption_by_date[]` of `acus_by_product.cascade + acus_by_product.terminal` — **not** `total_acus` (that includes Devin Cloud and review, which the cloud gate covers). Also derive `run_rate` (last-7-day average Local Agent ACUs/day) from the same endpoint with `time_after = now − 7d`.
4. **Current org limits.** For every org, GET `/v3beta1/enterprise/organizations/{org_id}/consumption/acu-limits`. Record `local_agent.cycle_acu_limit` as `cap_before` (null when unset). Note each org's `cloud_agent.cycle_acu_limit` for the preview — `slg` never touches the cloud gate.
5. **Plan the distribution.** Build the `org_caps_jq` input:
   ```json
   {"pool": <DAG_MONTHLY_ACU_POOL>, "min_headroom": 250, "days_left": <days left>,
    "orgs": [{"org_id": ..., "name": ..., "local_consumed": ..., "run_rate": ..., "cap_before": ...}, ...]}
   ```
   Run `jq -f <org_caps_jq>`. The default plan passes `"min_headroom": 250`; a value between 250 and 500 may be passed only when the user explicitly requests it in this session, and above 500 is never valid — the program clamps at 500 (hard rule 11 applies to this floor exactly as it does to user caps). Show the exact jq command and its complete JSON output (hard rule 1).
   - `{error}` output (pool cannot cover every org's floor): report the shortfall and stop — suggest raising `DAG_MONTHLY_ACU_POOL` or lowering consumption expectations; never scale an org below its own consumption to force a fit.
6. **Preview and confirm.** One table from `proposed`: org_id, name, Local Agent consumed, run_rate, projected, `cap_before → cap_after`, headroom, delta — plus `mode`, `sum_before`, `sum_after`, `pool`, `unallocated`, and every `warnings[]` line verbatim. Flag any org whose Σ member per-user caps exceeds its proposed org cap (org and user caps are independent gates; the tighter one bites first). State explicitly that `cloud_agent` caps are untouched. Print the UI instruction (hard rule 10): `app.devin.ai > Enterprise Settings > Consumption`. Then **stop**; write only after the user sends `CONFIRM DAG WRITE` (hard rule 2).
7. **PATCH every changed org.** For each org where `cap_after != cap_before`, PATCH `/v3beta1/enterprise/organizations/{org_id}/consumption/acu-limits` with body `{"local_agent":{"cycle_acu_limit":<cap_after>}}` — the body carries only the `local_agent` key so the cloud gate is preserved. Skip orgs whose cap is already the proposed value and say so.
8. **Live verify.** GET each changed org's ACU-limit resource after its PATCH; confirm `local_agent.cycle_acu_limit == cap_after` (hard rule 4). On the first failed PATCH or verification GET, quote the exact response body, perform no further PATCH or ledger update in this run, report applied / failed / unattempted rows, and offer a re-plan for only the remainder (hard rule 8).
9. **Update ledger.** Refresh org-level entries under the ledger's `orgs` key with `{org_id, name, cap, consumed}` and an updated timestamp, separate from per-user entries. Re-read the file and show the changed entries.
10. **Report.** Final table of applied caps, `sum_after` vs pool with `unallocated` slack, any warned orgs (projected to hit their gate early), and any org whose Σ per-user caps exceeds the new org cap. Point to `dag set limit global <acus> [org]` for a later explicit one-number adjustment, `dag set-limits-global` for zero-sum seeding of a newly added org, and `dag set-limits` for the per-user layer.
