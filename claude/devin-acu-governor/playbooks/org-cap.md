# Playbook: org-cap (change one org's Local Agent cap — funding mode asked before any raise)

Change the **org-level Local Agent cap** of exactly one billing organization, then — after the funding choice and the write gate — PATCH it (and any donor orgs) and live-verify. This is the explicit single-org change flow, sitting between the two neighbours: `dag set limit global <acus> [org]` writes one number deterministically with no planning, and `dag slg` replans every org's cap from consumption. `dag org-cap` plans one org's move with `org_rebalance_jq` and lets the operator pick **how the raise is funded**; the choice is asked before any raise and is never defaulted.

Run context supplies: `org selector` (an `org_id` or an org name), `requested amount` (exactly one of `+N ACUs above the current cap`, `set cap to N ACUs (absolute)`, or `none — recommend via auto-need (projected + target headroom)`), the funding-modes line, and the standard paths (`org_rebalance_jq`, `ledger`, `donor_record`, pool). Reference only those lines; do not invent others.

Funding modes (the exact keyword menu — each raise mode is a different `org_rebalance_jq` input over the same org data and the same single-org `needs`):

- `ZERO-SUM` — donor orgs fund the raise (`use_slack: false`). Σ org caps is unchanged; whatever donors cannot cover stays `unfunded`.
- `POOL HEADROOM` — donors give nothing; the raise is funded only from ceiling slack, `ceiling − Σ caps` (`slack_only: true`). Σ org caps grows by `slack_used` and never passes `DAG_MONTHLY_ACU_POOL`. This is NOT zero-sum and the preview must say so.
- `MIXED` — donors first, then ceiling slack for the remainder (`use_slack: true`). Σ org caps grows by `slack_used` only, never past the ceiling; NOT zero-sum when `slack_used > 0`.
- `CANCEL` — no plan, no writes, no ledger update; the run ends.

The org-gate policies in the common contract all hold (hard rule 16): the ceiling is Σ of **every** org's local + cloud caps (Vontier included, no parent/child hierarchy), no flow may push Σ past `DAG_MONTHLY_ACU_POOL`, an org cap is never cleared, and this flow never touches any org's `cloud_agent` gate. The keyword you ask for picks a plan; it never authorizes writes (hard rule 2).

## Steps

1. **Resolve the org.** GET `/v3/enterprise/organizations`. Match the selector against `org_id` exactly first, then against `name` case-insensitively and exactly (trim surrounding whitespace). If there is no match, or more than one org matches by name, stop: print the full org roster (`org_id`, `name`) and ask the user to rerun with an exact `org_id`. Never guess by substring. State the resolved `org_id` and `name` at the top of every report.
2. **Cycle + layer reads.** GET `/v3/enterprise/consumption/cycles`; current cycle = item with `after <= now < before`; show the dates and the `days_left` calculation (hard rule 9). For **every** org (not just the target — the donors and the ceiling need the whole layer), GET `/v3beta1/enterprise/organizations/{org_id}/consumption/acu-limits` (record `local_agent.cycle_acu_limit` as `cap_before`, null when unset, and `cloud_agent.cycle_acu_limit`) and GET `/v3/enterprise/consumption/daily/organizations/{org_id}` for the cycle window: `local_consumed` = Σ `acus_by_product.cascade + acus_by_product.terminal` (not `total_acus`), and `run_rate` = last-7-day average of the same Local Agent sum (`time_after = now − 7d`). Then run a **baseline** `jq -f <org_rebalance_jq>` over the assembled org rows with `"needs": []` (hard rule 1): its `sum_before`, `over_ceiling`, `overage`, and `uncapped_orgs` are the layer figures for this whole run — report `sum_before` vs `DAG_MONTHLY_ACU_POOL` and list every uncapped org (an unset `local_agent` gate makes the ceiling unenforceable). For the target org only, also read the member per-user layer so step 8 can flag it: GET `/v3/enterprise/members/users` (cursor pagination) for the roster, then GET `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits` for each member; a user belongs to the target when `billing_org_id` equals the resolved `org_id`, else when the target is the user's first accessible org (same attribution rule as `boost-org`). Any read failure stops the run with the exact response body (hard rule 3).
3. **Interpret the amount** from Run context `requested amount`, against the target's `cap_before`:
   - `+N` — a need of N ACUs above the current cap: `{"org_id": <target>, "need": N}`.
   - absolute `N` — compare with `cap_before`: `N > cap_before` is a raise with `need = N − cap_before`; `N < cap_before` is a **shrink** (step 4); `N == cap_before` is a no-op — say so and stop.
   - omitted — auto-need: `{"org_id": <target>, "need": "auto"}`, resolved by the program as `max(0, ceil(projected) + target_headroom − cap_before)`. Pass `"target_headroom": 250` by default; a value between 250 and 500 only when the user explicitly requests it in this session (name the request in the preview); above 500 is never valid — never pass a larger value: cap the input at 500, tell the user their requested headroom was reduced to the 500 backstop, and note that raising it requires changing repository policy (hard rule 11). A resolved need of 0 yields no recipient row: report "the current cap already holds projected consumption plus the target headroom — no change recommended" and stop.
   - **Uncapped target** (`cap_before` null): `+N` is invalid — there is no cap to be above; stop and ask the user for an absolute amount. An absolute `N = 0` is a block, not a cap change — refuse it and point at `dag set limit global 0 <org>`. Absolute (`N ≥ 1`) or omitted amounts model the target as `"local_cap": 0` in the jq input, and the preview must state that the first explicit cap counts as Σ growth (the org was unlimited, so the ceiling had not reserved room for it) and must be funded like any raise. Once modeled as `local_cap: 0`, the target no longer appears in the program's `uncapped_orgs` or its "no explicit cap" warning — the preview must name the target as previously uncapped itself.
4. **Shrink path** (absolute `N < cap_before`, integer `N ≥ 1`). No funding question: a shrink frees pool room and needs no donor or slack. All figures come from jq (hard rule 1): the step 2 baseline run supplies `sum_before` and the target's `consumed` and `projected`; run the baseline a second time with the target's `local_cap` set to `N` (still `"needs": []`) — that run's `sum_before` is the post-write Σ. Warn loudly when `N` is below the target's `consumed`, and also when it is below `projected` — members of that org are blocked at the org gate immediately (or will be before cycle end). Shrinks are always allowed, even when the layer is over the ceiling. Preview the single write: endpoint `/v3beta1/enterprise/organizations/{org_id}/consumption/acu-limits`, old → new, body `{"local_agent":{"cycle_acu_limit":<N>}}`, plus Σ before → after vs the ceiling (both jq-derived as above) and the UI instruction (hard rule 10). Stop; write only after `CONFIRM DAG WRITE` (hard rule 2). Then PATCH the `local_agent` key only, GET-verify `local_agent.cycle_acu_limit == N` (hard rule 4), refresh the ledger `orgs` entry (step 10), and report (step 11). Steps 5–9 do not apply.
5. **Raise guard.** If the step 2 baseline run reports `over_ceiling: true`, refuse every raise mode (`ZERO-SUM`, `POOL HEADROOM`, `MIXED`): print its `sum_before`, `ceiling`, and `overage`, say only the shrink path may run, and point at `dag slg` to replan the whole layer under the pool. Stop.
6. **Plan all three modes.** Build one input and run `jq -f <org_rebalance_jq>` three times, changing only the funding flags; the target is the only `needs` entry:
   ```json
   {"ceiling": <DAG_MONTHLY_ACU_POOL>, "min_donor_headroom": 250, "days_left": <n>, "target_headroom": 250,
    "full_shortfall": true,
    "orgs": [{"org_id", "name", "local_cap", "cloud_cap", "local_consumed", "run_rate"}, …every org, Vontier included],
    "needs": [{"org_id": <target>, "need": <N | "auto">}]}
   ```
   Add `"use_slack": false` for `ZERO-SUM`, `"use_slack": true` for `MIXED`, and `"slack_only": true` for `POOL HEADROOM`. `target_headroom` matters only for `"need": "auto"`. `"full_shortfall": true` is required in all three mode runs: this is an explicit operator request, so a numeric need funds in full instead of the boost-family absorb formula — the requested cap is reached or the gap is reported, never silently absorbed. Show each exact jq command and its complete JSON output (hard rule 1); every figure below comes from that output, never from manual arithmetic. A jq `{error}` output stops the run with the message quoted.
7. **Funding menu — asked before any raise preview (shrink path skips it).** Present one comparison table, one row per mode: funded from donors, funded from slack, `unfunded`, `sum_before → sum_after` vs `ceiling`, and the number of donor cuts. Say plainly which modes are zero-sum and which grow Σ org caps. Show `uncapped_orgs` next to the table: any uncapped org forces `ceiling_slack` to 0, so `POOL HEADROOM` and `MIXED` can fund nothing from slack until every org is capped — say so when it applies. Then ask for exactly one keyword — `ZERO-SUM`, `POOL HEADROOM`, `MIXED`, or `CANCEL` — and stop for the reply. Do not recommend-and-proceed, do not pre-select a default, and do not continue on silence. `CANCEL` ends the run: no writes, no ledger update. The keyword picks a plan for the preview; it never authorizes writes — a `CONFIRM DAG WRITE` sent at this menu stage selects no mode and authorizes nothing (hard rule 2 requires it after the step 8 preview).
8. **Preview the chosen plan.** Using only the chosen mode's jq output show: the recipient row (`cap_before → cap_after`, `need`, `from_donors`, `from_slack`, `unfunded`); the donor table (`cap_before → cap_after`, `given`, `floor`); `sum_before → sum_after` vs `ceiling`; every `warnings[]` line verbatim; each write as endpoint, old → new, body `{"local_agent":{"cycle_acu_limit":<cap_after>}}`. State the requested cap (or `+N` target) next to the jq `cap_after` and flag any gap between them explicitly, even when `unfunded` is 0. If `unfunded > 0`, say the requested amount is not fully reachable and that the shortfall stays blocked at the org gate — offer the other keyword plans or `CANCEL`; never hand-raise past the jq `cap_after` and never lower a donor floor (hard rules 11, 12). Flag when the target org's Σ member per-user caps exceeds the proposed org cap (org and user caps are independent gates; the tighter one bites first). Print the UI instruction (hard rule 10): `app.devin.ai > Enterprise Settings > Consumption`. Then stop; write only after the user sends `CONFIRM DAG WRITE` (hard rule 2). Any change of mode, amount, or donors requires a new preview and a new `CONFIRM DAG WRITE`.
9. **PATCH + verify.** PATCH every `writes[]` org at `/v3beta1/enterprise/organizations/{org_id}/consumption/acu-limits` with body `{"local_agent":{"cycle_acu_limit":<cap_after>}}` — local key only, so each cloud gate is preserved. PATCH donor cuts before the recipient raise, so Σ org caps never passes through a state above its final value. GET each changed org after its PATCH and confirm `local_agent.cycle_acu_limit == cap_after` (hard rule 4). On the first failed PATCH or verification GET, quote the exact response body, stop all further PATCHes, and report applied / failed / unattempted rows; offer a re-plan for only the remainder (hard rule 8). Rows already applied and GET-verified ARE recorded in the ledger's `orgs` key in step 10; failed and unattempted rows are not, and the report must say the ledger reflects only the applied subset.
10. **Update ledger.** Refresh the `orgs` entries in the ledger for every changed org with `{org_id, name, cap, consumed}` and an updated timestamp, separate from the per-user entries. Re-read the file and show the changed entries. Org-cap moves touch org caps only; no per-user cap changes, so the donor record is not updated.
11. **Report.** Resolved org, requested amount and how it was interpreted, funding mode chosen, applied rows (`cap_before → cap_after` for the target and each donor), `sum_before → sum_after` vs the ceiling, any `unfunded` remainder, and any org whose Σ per-user caps exceeds its org cap. Print the UI instruction (hard rule 10). Point to `dag slg` for a whole-layer replan and to `dag set limit global <acus> [org]` for a no-planning deterministic write.
