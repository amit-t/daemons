# Playbook: boost all (One plan for every OVER/CRITICAL/WARNING user)

Find every engineer needing attention right now — dashboard `OVER` (`consumed >= effective cap`, plus `cap == 0` with `consumed > 0`), `CRITICAL` (`0.95 <= consumed/cap < 1`), and `WARNING` (`0.85 <= consumed/cap < 0.95`) — and run the Boost + Borrow flow for all of them in **one combined run**: one live discovery, one shared donor pool, one batch preview, one `CONFIRM DAG WRITE`. This is the superset of `boost over` + `boost critical` + `boost warning`; no email is given — the recipient sets are discovered live. Fund every Boost zero-sum by Borrowing from the highest-projected-safe-surplus donors, keeping total allocation (Σ caps) unchanged unless the user explicitly accepts pool-headroom overage risk.

Band definitions match the dashboard's `user_status` in `lib/dashboard.jq`: effective cap = explicit per-user Local Agent override if set, else the org default user limit; unlimited/None caps are never in any band; `cap == 0` with `consumed == 0` is `blocked`, not boosted.

**Donor-record suppression (hard rule 13) applies before anything else**: a recorded current-cycle donor whose `consumed < 0.85 × baseline_cap` is in `DONOR` state — their high ratio is an artifact of DAG lowering their cap, not of real usage. They are never recipients in this run.

## Steps

1. **Cycle + roster + consumption + enterprise forecast.** GET `/v3/enterprise/consumption/cycles` for the current cycle. GET `/v3/enterprise/members/users` for the roster and build an email ↔ user_id map. Get current-cycle per-user ACUs: one Windsurf `consumption` call (`group_by=user`, cycle start → today) if the key is available, else loop `/v3/enterprise/consumption/daily/users/{user_id}`. URL-encode every `user_id` path segment. In the same step, GET `/v3/enterprise/consumption/daily` for the cycle window and compute `projected_cycle_total = total_acus / elapsed_days × cycle_days` — the enterprise forecast used by every recipient's plan in step 7 (rule 14). Compute this from the live data fetched here, never from a stale dashboard file.
2. **Read live current limits.** GET `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits` for the whole roster. Prefer live `local_agent.cycle_acu_limit`; fall back to the org default user limit; treat unset/None as unlimited.
3. **Read the donor record and mark DONOR state.** Read the donor record (`donor_record` in Run context). It is live only when its `cycle_start` equals the current cycle's `after` epoch; a stale record is ignored entirely. For every roster user compute `effective_cap`, `ratio = consumed / effective_cap`, and the raw band. A user whose raw band is over/critical/warning **and** who has a live donor entry **and** whose `consumed < 0.85 × baseline_cap` is `DONOR` — remove them from every recipient set.
4. **Select the combined recipient set.** From the non-DONOR users keep: the over set (`consumed >= cap`, finite cap, plus `cap == 0` with `consumed > 0`), the critical set (`0.95 <= ratio < 1`), and the warning set (`0.85 <= ratio < 0.95`). Order recipients most urgent first: over (most-over first), then critical (highest ratio first), then warning (highest ratio first). If all three sets are empty, report "no users are currently over budget or in the warning/critical bands" (plus any DONOR-suppressed users) and stop — nothing to boost.
5. **Report the sets first.** Print one table of every recipient: email, band (`OVER`/`CRITICAL`/`WARNING`), consumed, effective_cap, ratio (%), headroom (`cap - consumed`, negative when over), and — when `run_rate` is available — estimated days until `OVER`. Then a second table of every `DONOR`-suppressed user: email, consumed, current cap, `baseline_cap`, `given_total`, with the note that they are excluded per hard rule 13. State the counts: "N over, N critical, N warning; N donor-suppressed".
6. **Shared donor pool — usage patterns, not just the bottom of the table.** Rank Borrow candidates across the roster (excluding every recipient) by highest projected safe surplus: compute each donor's `run_rate` (last-7-day average ACUs/day, from the Windsurf daily-granularity call or `/v3/enterprise/consumption/daily/users/{user_id}` with `time_after = now − 7d`) and `days_left` in the cycle, exactly as the `boost` playbook does. `DONOR`-suppressed users are first-class donor candidates — their low usage is exactly why they were donors — but the planner's safety floors protect them like anyone else. This single donor pool funds all Boosts in this run; track each donor's remaining headroom as it is spent so no donor is double-counted or cut below its own consumption (or projected end-of-cycle consumption when `run_rate` is known). Fetch `run_rate` for every donor candidate — `boost_plan_jq` excludes any donor without it by default (`require_forecast`), reported per recipient plan in `donors_excluded_no_forecast`; do not hand-drop or hand-add donors around that exclusion.
7. **Plan each recipient (sequential).** For each recipient in the step-4 order, build the `boost_plan_jq` input exactly as `boost` does:
   ```json
   {"pool": <DAG_MONTHLY_ACU_POOL>, "share": <pool / N>,
    "recipient_buffer": 0.15, "donor_buffer": 0.10,
    "max_headroom": 250, "days_left": <days left in cycle>,
    "min_donor_headroom": 25, "require_forecast": true,
    "recipient": {"email": ..., "cap": ..., "consumed": ..., "run_rate": ..., "days_left": ...},
    "donors": [{"email": ..., "cap": ..., "consumed": ..., "run_rate": <last-7d ACUs/day>}, ...]}
   ```
   When the enterprise projection from step 1 is UNDER pool, also add `"forecast": {"pool": <DAG_MONTHLY_ACU_POOL>, "projected_cycle_total": <live linear projection>, "utilization": 0.5}`. Shared forecast headroom is a single budget across the whole batch, exactly like donor caps: pass the *remaining* forecast headroom to each sequential recipient's plan, decremented by the `forecast_funded` already spent by earlier recipients in this run.
   Use the *current remaining* donor headroom (caps already reduced by earlier recipients in this run) so the zero-sum invariant holds across the whole batch. `"max_headroom": 250` is the default per hard rule 11; a larger value (500 maximum) only on explicit in-session user request, never above 500. `"min_donor_headroom": 25` is the jq built-in donor backstop (hard rule 11); never pass a lower value. No `delta_override` — each recommendation comes from that user's own run-rate projection (`ceil(projected_month_end × 1.15)`, clamped to consumed + `max_headroom`) and is planning input only. A critical/warning-band user whose run-rate projection stays under their current cap needs no boost — drop them from the plan and say so in the report; the badge alone is not a reason to move ACUs. Run `jq -f <boost_plan_jq>`. Carry the resulting donor `cap_after` values forward as the donors' new baselines for the next recipient, and carry the resulting `forecast_headroom − forecast_funded` forward as the remaining shared forecast budget.
8. **Batch preview.** Show one combined before/after table: every recipient Boost (band, cap_before → cap_after) and every donor Borrow (cap_before → cap_after, total given across the batch), plus per-recipient `projected_month_end`, `delta`, `forecast_funded`, `donor_funded`, `funded`, and the batch `Σ caps before` vs `Σ caps after`. When any recipient's `forecast_funded > 0`, call out the total `forecast_funded` across recipients, the Σ-caps growth, and that the batch is NOT zero-sum (`Σ caps after == Σ caps before + total forecast_funded`); otherwise prove `Σ caps before == Σ caps after`. Surface every warning, including every recipient's `donors_excluded_no_forecast`. If any recipient has `shortfall > 0`, stop and ask the user to choose exactly one keyword per affected recipient: `PARTIAL`, `CHANGE DONORS`, `POOL HEADROOM` (run `boost_check_jq`; raises total exposure/overage risk), or `CANCEL`. **Never lower donor safety thresholds.** Any non-cancel choice requires replanning, a new complete preview, and `CONFIRM DAG WRITE`.
9. **Confirm.** List exactly which users will be PATCHed and to what value, then stop. Write only after the user sends `CONFIRM DAG WRITE` in a later same-session message covering the whole batch (hard rule 2).
10. **PATCH changed users.** PATCH `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits` for every recipient and every donor with body `{"local_agent":{"cycle_acu_limit":<new_cap>}}`. A user override replaces the default. Apply recipients and donors together so the allocation stays balanced.
11. **Live verify.** GET every changed user limit after PATCH. Confirm `local_agent.cycle_acu_limit` equals the planned value for each recipient and donor. On the first failed PATCH or verification GET, quote the exact response body and perform no further PATCH, DELETE, or ledger update in this run; report applied, failed, and unattempted rows, then offer a new read-and-preview run for only that subset.
12. **Update ledger + donor record.** Refresh changed entries in the ledger with `{user_id, cap, consumed}` and an updated timestamp; re-read the file and show changed entries (batch `sum_caps` unchanged when no shortfall was covered from headroom). Then update the donor record per hard rule 13: for every donor whose cap this run reduced, append the reduction `{at, given, cap_before, cap_after, recipient: "boost-all batch", command: "boost all"}`, set sticky `baseline_cap` on first reduction this cycle, and update `cap_after`/`given_total`/`last_given_at`; create the file fresh with the current cycle epochs if missing or stale. A recipient with a donor entry whose new cap reaches or passes their `baseline_cap` may have their donor entry removed — they are made whole.
13. **UI instruction.** Print: `app.devin.ai > Enterprise Settings > Consumption` to see current-cycle Local Agent usage by product/user. Note that configured Local Agent limits are API-managed and this run's GET verification is the proof.
14. **Org-gate check (hard rule 15).** After the confirmed writes and live verification above, GET `/v3beta1/enterprise/organizations/{org_id}/consumption/acu-limits` for the billing org of every user changed this run. Sum each affected org's Σ explicit member `local_agent.cycle_acu_limit` (roster `billing_org_id` attribution) and compare it to that org's own `local_agent.cycle_acu_limit`. If Σ member caps exceeds an org cap, report the overcommit (org name, org cap, Σ member caps, overage) and offer a PATCH preview raising the org cap to `Σ member caps` or clearing it — a separate write requiring its own `CONFIRM DAG WRITE`. If no affected org is overcommitted, state that explicitly.
