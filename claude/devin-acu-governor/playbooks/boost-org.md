# Playbook: boost org (boost all, scoped to one organization)

Run the `boost all` flow — every `OVER`, `CRITICAL`, and `WARNING` user in one combined run — with **both recipients and donors restricted to members of one organization**. The org selector is in Run context (`org selector`); it is an `org_id` or an org name. Users billed to any other org are never recipients, never donors, and never PATCHed in this run. Everything else — band definitions, DONOR-state suppression (hard rule 13), donor safety floors, forecast rules, the preview, the `CONFIRM DAG WRITE` gate, live-GET verification, ledger and donor-record updates — is exactly the `boost all` contract.

Because recipients and donors come from the same org, the donor-funded part of the plan nets to zero inside that org and needs no org-gate move. Only `forecast_funded` ACUs grow the org's member caps; those go through the org-gate zero-sum rebalance (hard rule 15) like any other flow.

## Steps

1. **Resolve the org.** GET `/v3/enterprise/organizations`. Match the selector against `org_id` exactly first, then against `name` case-insensitively and exactly (trim surrounding whitespace). If there is no match, or more than one org matches by name, stop: print the full org roster (`org_id`, `name`) and ask the user to rerun with an exact `org_id`. Never guess by substring. State the resolved `org_id` and `name` at the top of every report.
2. **Cycle + roster + consumption + enterprise forecast.** Same as `boost all` step 1: GET `/v3/enterprise/consumption/cycles`; GET `/v3/enterprise/members/users` for the roster and the email ↔ user_id map; current-cycle per-user ACUs (Windsurf `consumption` `group_by=user`, else loop `/v3/enterprise/consumption/daily/users/{user_id}`); GET `/v3/enterprise/consumption/daily` for the cycle window and compute `projected_cycle_total = total_acus / elapsed_days × cycle_days` (rule 14). URL-encode every `user_id` path segment.
3. **Read live limits and billing org.** GET `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits` for the whole roster. Keep `local_agent.cycle_acu_limit` (fall back to the org default user limit; unset/None = unlimited) and `billing_org_id`. A user is an **org member** when `billing_org_id` equals the resolved `org_id`; when `billing_org_id` is absent, use the user's first accessible org from the roster (the same attribution rule the org-gate rebalance uses). Drop every non-member now; report the member count and the count of users whose membership came from the fallback.
4. **Read the donor record and mark DONOR state.** Same as `boost all` step 3, over org members only.
5. **Select the org recipient set.** Same as `boost all` step 4, over org members only: over set, then critical set, then warning set, most urgent first. If all three are empty, report "no users in <org name> are currently over budget or in the warning/critical bands" (plus any DONOR-suppressed members) and stop.
6. **Report the sets first.** Same tables and counts as `boost all` step 5, titled with the org name.
7. **Org donor pool.** Same as `boost all` step 6, but the candidates are org members only (excluding every recipient). Fetch `run_rate` for every candidate. Never add a donor from another org, even to cover a shortfall.
8. **Plan each recipient (sequential).** Same as `boost all` step 7 (`boost_plan_jq`, `"max_headroom": 250`, `"min_donor_headroom": 25`, `"require_forecast": true`, shared `forecast.remaining` budget, donor caps carried forward), with the `donors` array holding only org members.
9. **Batch preview.** Same as `boost all` step 8, with the org name and `org_id` in the header. Prove every changed row belongs to the resolved org. On `shortfall > 0`, offer the same keywords (`PARTIAL`, `CHANGE DONORS`, `POOL HEADROOM`, `CANCEL`); `CHANGE DONORS` still means org members only — to borrow across orgs the user must run `dag boost all` instead. **Never lower donor safety thresholds.** Include the org-gate rebalance table from step 14 in this same preview.
10. **Confirm.** List exactly which users will be PATCHed and to what value, then stop. Write only after the user sends `CONFIRM DAG WRITE` in a later same-session message covering the whole batch (hard rule 2).
11. **PATCH changed users.** PATCH `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits` for every recipient and donor with body `{"local_agent":{"cycle_acu_limit":<new_cap>}}`.
12. **Live verify.** GET every changed user limit after PATCH. On the first failed PATCH or verification GET, quote the exact response body, stop all further writes, and report applied, failed, and unattempted rows.
13. **Update ledger + donor record.** Same as `boost all` step 12, with `recipient: "boost-org batch <org name>"` and `command: "boost.org <org_id>"` on each donor reduction.
14. **Org-gate zero-sum rebalance (hard rule 15).** Follow "Org-gate zero-sum rebalance" in the common contract. Donor-funded Boosts net to zero inside the org, so the org's net member-cap growth equals the batch's total `forecast_funded`. When that is 0, `needs` is empty: say so explicitly and state that `writes` is empty. Otherwise plan the zero-sum org move with `org_rebalance_jq` before the preview and write it under the same `CONFIRM DAG WRITE`, then GET-verify.
15. **UI instruction.** Print: `app.devin.ai > Enterprise Settings > Consumption` to see current-cycle Local Agent usage by product/user.
