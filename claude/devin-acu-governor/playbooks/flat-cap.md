# Playbook: flat-cap (Flat per-user Local Agent cap with a consumption floor)

Set the **same explicit Local Agent cap** (the flat amount in Run context) for every active current-member engineer. The one exception is the consumption floor: a user whose current-cycle Local Agent consumption already exceeds the flat amount gets at least `ceil(consumed)` — **never set a cap below consumption**. Unlike `set-limits` (prorated shares) and `set-limits-new` (zero-sum seeding of the uncapped only), `flat-cap` normalizes the whole active layer to one number: it writes new caps, raises caps below the flat, and reduces caps above it. It is deliberately **not zero-sum at the user layer** — Σ explicit user caps moves to wherever the flat lands it — but the org gates still move zero-sum under the enterprise ceiling (hard rules 15 and 16).

Target active current-member engineers only. Show the included roster and the excluded/inactive users for scope approval; do not assume every enterprise member is an engineer. All proposed caps and sums come from `flat_cap_jq` (hard rule 1).

## Steps

1. **Cycle dates.** GET `/v3/enterprise/consumption/cycles`. Current cycle = item with `after <= now < before`. Convert epochs to dates and compute `days_left` and elapsed days (hard rule 9).
2. **Roster / user IDs.** GET `/v3/enterprise/members/users` (paginate via `end_cursor`). Build current-member rows `{email, user_id, name, member: true}`. URL-encode every `user_id` in endpoint paths (it can contain `|`).
3. **Per-user Local Agent consumption.** The floor is **Local Agent** consumption, not total ACUs:
   - Windsurf key available: one GET `consumption` (`product=agent`, `group_by=user`, `granularity=daily`, `start_date`=cycle start, `end_date`=today, `page_size=10000`; follow `next_page_cursor`). Sum `billed_acus` per `user_email` for `consumed`, and derive each user's last-7-day `run_rate` from the daily rows. Mind the 10/hour rate limit (hard rule 5) — this one call serves consumption and run rates for the whole run.
   - No Windsurf key: loop GET `/v3/enterprise/consumption/daily/users/{user_id}` (URL-encoded) over the roster with the cycle's `time_after`/`time_before`; `consumed` = Σ `acus_by_product.cascade + acus_by_product.terminal` (the Local Agent products; `devin` is Cloud and `review` is not Local Agent). Batch with `xargs -P4`. Derive `run_rate` from a second 7-day-window pass only if the user asks for forecasts; otherwise omit `run_rate` (and then omit `days_left`-dependent projections).
4. **Activity filter — active current members only.** With a Windsurf key, POST `/api/v1/UserPageAnalytics`, join `userTableStats[]` by email, and set `active: true` only when `teamStatus` is active (case-insensitive); missing, inactive, disabled, removed, or former rows default to `active: false`. Without a Windsurf key, set `activity_evidence: unavailable`, treat every current roster member as provisionally eligible **for preview only**, and require the user to confirm the final eligible list before planning.
5. **Read live current limits.** For every roster user, GET `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits`. The GET returns the **explicit override only** (`cap_before`; unset = no explicit cap). Also record each user's `billing_org_id` when present (explicit setting first, else first accessible org from the roster) — the org-gate rebalance needs it.
6. **Scope approval — not write authorization.** Show two tables and stop for the user's reply:
   - **Included:** every active current-member user — email, user_id, consumed, current explicit cap (or unset).
   - **Excluded:** inactive/former/non-member users with reasons, plus any roster rows without activity evidence.
   Ask the user to confirm the included list or name exclusions (service accounts, non-engineers). Scope approval does not authorize any PATCH or DELETE — the separate `CONFIRM DAG WRITE` gate still applies (hard rule 2).
7. **Plan with `flat_cap_jq`.** Build the input and run `jq -f <flat_cap_jq>`; show the exact command and its complete JSON output (hard rule 1):
   ```json
   {"flat_cap": <amount from Run context>, "max_headroom": 250, "days_left": <n>,
    "users": [{"email": ..., "user_id": ..., "consumed": <Local Agent ACUs>,
               "cap": <explicit cap or omit>, "member": true|false, "active": true|false,
               "run_rate": <last-7d ACUs/day>, "billing_org_id": "<org_id>"}, ...]}
   ```
   `"max_headroom": 250` is the default per hard rule 11 (a flat amount above it clamps low consumers to `consumed + max_headroom`; 250–500 only on explicit in-session request, above 500 never — the jq built-in 500 is the backstop). The planner returns `caps[]` (write rows: `cap_before → cap`, `change` = new/raise/reduce), `unchanged[]` (no write), `raised_above_flat[]` (consumption-floor users), `sum_before`/`sum_after`/`delta`, `org_deltas[]` (net explicit-cap movement per billing org), `excluded_users[]`, and `warnings[]`. Use these values exactly; surface every warning verbatim, including clamps, tight-headroom (< 25 ACUs) rows, projection overruns, and unresolved `billing_org_id` attribution.
8. **Org-gate zero-sum rebalance (hard rule 15).** Follow "Org-gate zero-sum rebalance" in the common contract: feed each positive `org_deltas` entry as a `needs` row into `org_rebalance_jq` with every org's live caps, Local Agent consumption (`acus_by_product.cascade + acus_by_product.terminal`), and run rates; show the exact command and full JSON output. Negative `org_deltas` (reductions) free org headroom and need no move. The org moves go in the same preview and the same `CONFIRM DAG WRITE` — never a follow-up proposal. Σ org caps stays ≤ `DAG_MONTHLY_ACU_POOL`; unfunded room is reported as blocked at the org gate, never fixed by raising the layer (hard rule 16).
9. **Preview and confirm.** Show, endpoint by endpoint, every planned write: the exact endpoint with the real URL-encoded user_id, old value from the live GET, new value, and JSON body `{"local_agent":{"cycle_acu_limit":<cap>}}` — the user rows (new/raise/reduce, consumption-floor rows flagged), the `unchanged` rows (no write), and the zero-sum org-move table from step 8. Show `sum_before → sum_after` (`delta`) for the user layer and `sum_before == sum_after` vs the ceiling for the org layer. Print the UI instruction: `app.devin.ai > Enterprise Settings > Consumption` (hard rule 10). Then **stop**; write only after the user sends `CONFIRM DAG WRITE` (hard rule 2).
10. **PATCH changed users.** For each `caps[]` row, PATCH `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits` with body `{"local_agent":{"cycle_acu_limit":<cap>}}`. Never PATCH an `unchanged` or excluded row, and never include `billing_org_id` unless the user explicitly asked to change attribution.
11. **Live verify.** GET each changed user limit after PATCH and confirm `local_agent.cycle_acu_limit` equals the planned cap. On the first failed PATCH or verification GET, quote the exact response body and perform no further PATCH, DELETE, or ledger update in this run; report applied, failed, and unattempted rows and offer a resume covering only the failed/unattempted subset (hard rules 3, 4, 8).
12. **Org writes.** After the user PATCHes verify, PATCH each `org_rebalance_jq` `writes[]` org with `{"local_agent":{"cycle_acu_limit":<cap_after>}}` (local key only) and GET-verify each, under the same stop-on-first-failure rule.
13. **Ledger + donor record.** Refresh the ledger (path in Run context) for every changed user with `{user_id, cap, consumed}`, record org moves under the `orgs` key, and re-read to show the changed entries. Then update the donor record per hard rule 13: every `reduce` row is a recorded reduction (`at`, `given` = `cap_before − cap`, `cap_before`, `cap_after`, `recipient: "flat-cap batch"`, `command: "flat-cap"`), with `baseline_cap` sticky; create the file fresh with the current cycle epochs when missing or stale. A `raise` row that restores a recorded donor to `baseline_cap` or above removes their donor entry.
14. **Report.** Summarize: users set to the flat cap, consumption-floor users (`raised_above_flat`), reductions recorded as donor entries, unchanged rows, excluded users, org moves, and any org-gate room left unfunded (blocked by design). Point to `dag boost <email> [acus]` for single-user top-ups.
