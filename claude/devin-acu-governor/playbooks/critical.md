# Playbook: boost critical (Boost everyone in the red zone about to go over)

Find every engineer whose current-cycle consumption is in the dashboard's red `CRITICAL` band — `0.95 <= consumed / effective cap < 1` — then run the same Boost + Borrow flow as `boost` for each one — no email is given, the recipient set is discovered live at run time. This is the urgent subset of `boost warning`: only the red badges (95–100% of cap), the users who will tip into `OVER` within hours or days, skipping the yellow 85–95% band entirely. Fund each Boost zero-sum by Borrowing from the lowest consumers, keeping total allocation (Σ caps) unchanged unless the user explicitly accepts pool-headroom overage risk. There is no `boost target` in Run context; the targets are whoever is in the critical band right now.

`CRITICAL` band definition (matches the dashboard's `user_status` in `lib/dashboard.jq`): a user's effective cap is their explicit per-user Local Agent override if set, else the org default user limit. A user is in the critical band when the cap is a finite non-zero number and `0.95 <= consumed / cap < 1`. Users at or past their cap (`consumed >= cap`) belong to `boost over`, not this run — report them separately and point at `dag boost over`. Users in the yellow band (`0.85 <= ratio < 0.95`) belong to `boost warning` — report their count with a pointer to `dag boost warning`, do not fold them into this run. Unlimited/None caps and `cap == 0` users are never in the critical band.

## Steps

1. **Cycle + roster + consumption.** GET `/v3/enterprise/consumption/cycles` for the current cycle. GET `/v3/enterprise/members/users` for the roster and build an email ↔ user_id map. Get current-cycle per-user ACUs: one Windsurf `consumption` call (`group_by=user`, cycle start → today) if the key is available, else loop `/v3/enterprise/consumption/daily/users/{user_id}`. URL-encode every `user_id` path segment.
2. **Read live current limits.** GET `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits` for the whole roster. Prefer live `local_agent.cycle_acu_limit`; fall back to the org default user limit; treat unset/None as unlimited.
3. **Select the critical set.** Compute each user's `effective_cap` and `ratio = consumed / effective_cap`. Keep every user with a finite non-zero cap and `0.95 <= ratio < 1`. Then apply donor-record suppression (hard rule 13): read the donor record (`donor_record` in Run context; live only when its `cycle_start` equals the current cycle's `after`), and drop every would-be recipient with a live donor entry and `consumed < 0.85 × baseline_cap` — list them separately as `DONOR` (consumed, current cap, `baseline_cap`); their band is an artifact of a DAG cap reduction and they are not boosted. The remainder is the recipient set. If any users are already `OVER` (`ratio >= 1`), list them separately with a pointer to `dag boost over` — do not fold them into this run. If any users sit in the yellow band (`0.85 <= ratio < 0.95`), state their count with a pointer to `dag boost warning` — also not part of this run. If the critical set is empty, report "no users are currently in the critical band (95–100% of cap)" (plus any DONOR-suppressed users) and stop — nothing to boost.
4. **Report the critical set first.** Print a table of every critical-band user: email, consumed, effective_cap, ratio (%), remaining headroom (`cap - consumed`), and — when `run_rate` is available — estimated days until `OVER` (`(cap - consumed) / run_rate`), sorted highest ratio first. State the count: "N users in the critical band". This is the answer to "who goes over next".
5. **Shared donor pool — usage patterns, not just the bottom of the table.** Rank Borrow candidates across the roster (excluding the critical set, the yellow warning band, and any `OVER` users) by highest projected safe surplus: compute each donor's `run_rate` (last-7-day average ACUs/day, from the Windsurf daily-granularity call or `/v3/enterprise/consumption/daily/users/{user_id}` with `time_after = now − 7d`) and `days_left` in the cycle, exactly as the `boost` playbook does. This single donor pool funds all Boosts in this run; track each donor's remaining headroom as it is spent so no donor is double-counted or cut below its own consumption (or projected end-of-cycle consumption when `run_rate` is known).
6. **Plan each recipient (sequential).** For each critical-band user, highest ratio first, build the `boost_plan_jq` input exactly as `boost` does:
   ```json
   {"pool": <DAG_MONTHLY_ACU_POOL>, "share": <pool / N>,
    "recipient_buffer": 0.15, "donor_buffer": 0.10,
    "max_headroom": 250, "days_left": <days left in cycle>,
    "recipient": {"email": ..., "cap": ..., "consumed": ..., "run_rate": ..., "days_left": ...},
    "donors": [{"email": ..., "cap": ..., "consumed": ..., "run_rate": <last-7d ACUs/day>}, ...]}
   ```
   Use the *current remaining* donor headroom (caps already reduced by earlier recipients in this run) so the zero-sum invariant holds across the whole batch. `"max_headroom": 250` is the default per hard rule 11; a larger value (500 maximum) only on explicit in-session user request, never above 500. No `delta_override` — each recommendation comes from that user's own run-rate projection (`ceil(projected_month_end × 1.15)`, clamped to consumed + `max_headroom`) and is planning input only. A critical-band user whose run-rate projection stays under their current cap needs no boost — drop them from the plan and say so in the report; the badge alone is not a reason to move ACUs. Run `jq -f <boost_plan_jq>`. Carry the resulting donor `cap_after` values forward as the donors' new baselines for the next recipient.
7. **Batch preview.** Show one combined before/after table: every recipient Boost (cap_before → cap_after) and every donor Borrow (cap_before → cap_after, total given across the batch), plus per-recipient `projected_month_end`, `delta`, `funded`, and the batch `Σ caps before == Σ caps after` (zero-sum across the whole run). Surface every warning. If any recipient has `shortfall > 0`, stop and ask the user to choose exactly one keyword per affected recipient: `PARTIAL`, `CHANGE DONORS`, `POOL HEADROOM` (run `boost_check_jq`; raises total exposure/overage risk), or `CANCEL`. **Never lower donor safety thresholds.** Any non-cancel choice requires replanning, a new complete preview, and `CONFIRM DAG WRITE`.
8. **Confirm.** List exactly which users will be PATCHed and to what value, then stop. Write only after the user sends `CONFIRM DAG WRITE` in a later same-session message covering the whole batch (hard rule 2).
9. **PATCH changed users.** PATCH `/v3beta1/enterprise/users/{user_id}/consumption/acu-limits` for every recipient and every donor with body `{"local_agent":{"cycle_acu_limit":<new_cap>}}`. A user override replaces the default. Apply recipients and donors together so the allocation stays balanced.
10. **Live verify.** GET every changed user limit after PATCH. Confirm `local_agent.cycle_acu_limit` equals the planned value for each recipient and donor. On the first failed PATCH or verification GET, quote the exact response body and perform no further PATCH, DELETE, or ledger update in this run; report applied, failed, and unattempted rows, then offer a new read-and-preview run for only that subset.
11. **Update ledger + donor record.** Refresh changed entries in the ledger with `{user_id, cap, consumed}` and an updated timestamp. Re-read the file and show changed entries. With no shortfall covered from headroom, batch `sum_caps` is unchanged. Then update the donor record per hard rule 13: append each donor's reduction (`at`, `given`, `cap_before`, `cap_after`, recipient/batch label, `command: "boost critical"`), keep `baseline_cap` sticky, update `cap_after`/`given_total`/`last_given_at`; create the file fresh with the current cycle epochs when missing or stale, and remove any recipient's donor entry whose new cap reaches their `baseline_cap`.
12. **UI instruction.** Print: `app.devin.ai > Enterprise Settings > Consumption` to see current-cycle Local Agent usage by product/user. Note that configured Local Agent limits are API-managed and this run's GET verification is the proof.
